Tabs und SideNav

Zwei fertige Komponenten für Navigation: Tabs für horizontales Umschalten zwischen Inhalten, SideNav für vertikale Sidebar-Navigation mit Icons.

Tabs

Tabs organisieren Inhalte in horizontale Reiter. Klick auf einen Tab zeigt dessen Inhalt:

Was passiert hier?

  • Tabs – der Container für alle Tabs
  • defaultValue "Home" – welcher Tab beim Start aktiv ist
  • Tab "Label" – ein einzelner Tab mit seinem Label
  • Kinder von Tab – der Inhalt, der bei Auswahl erscheint
PropertyBeschreibung
defaultValue "name"Anfangs aktiver Tab
Tab "Label"Tab mit sichtbarem Label
Tipp: Der Tab-Inhalt kann beliebig komplex sein – Frames, Listen, Formulare. Tabs eignen sich für Einstellungsseiten, Dashboards oder Produktdetails.

SideNav

SideNav ist eine vertikale Navigation mit Icons – typisch für Dashboards und Admin-Panels:

Was passiert hier?

  • SideNav – der Container mit w 200 für die Breite
  • defaultValue – welches Item beim Start ausgewählt ist
  • NavItem "Label" – ein Navigationselement
  • icon "name" – Lucide-Icon vor dem Label
  • value "key" – interner Wert für die Auswahl

Mit Badges

Badges zeigen Zähler oder Status an – ideal für ungelesene Nachrichten oder Benachrichtigungen:

Tipp: SideNav eignet sich für App-Shells mit fester Sidebar. Kombiniere es mit einem Content-Bereich rechts davon.

App-Shell: SideNav + Content

In echten Apps lebt SideNav nie für sich allein – sie steht links, rechts daneben kommt der eigentliche View-Bereich. Das klassische Layout ist hor + w full, h full:

Das Pattern:

  • Outer Frame hor – horizontale Anordnung
  • SideNav mit fester w – feste Sidebar-Breite
  • Content-Frame mit grow – nimmt restlichen Platz

Navigation + show: Routing zwischen Views

Die statischen Beispiele oben zeigen die Navigation, aber wechseln den Content nicht. Mit show aus Kapitel 10 wird daraus echtes Routing – jedes NavItem referenziert einen View:

Was passiert: Klick auf ein NavItem → der zugehörige View wird sichtbar, die anderen werden ausgeblendet. Die Views liegen im selben Content-Frame nebeneinander; hidden auf den nicht-aktiven Views macht sie unsichtbar bis zur Auswahl.

Für richtig große Apps lebt jeder View in einer eigenen Datei. Statt lokaler Definitionen referenzierst du sie via show ViewName from Datei – siehe Kapitel 10 → "Komplettes Beispiel: App in vier Dateien".

Die from-Klausel

Hinter show ViewName kann optional from path/to/file stehen — ein Quelldatei-Hinweis ohne Dateiendung, slash-getrennt. Das macht für den Leser sichtbar, in welcher Datei der View definiert ist:

NavItem "Dashboard", icon "home", show DashboardView from screens/dashboard
NavItem "Projects", icon "folder", show ProjectsView from screens/projects
NavItem "Settings", icon "settings", show SettingsView from screens/settings

Die Klausel ist dokumentierend, nicht zwingend: der Multi-File-Loader findet alle screens/*.mir-Dateien automatisch. from hilft Studio und Validator, beim Klick direkt zur richtigen Datei zu springen.

Tabs mit show: Content auslagern

Genauso funktioniert show in Tabs. Wenn der Tab-Inhalt komplex ist (Forms, Listen, Sub-Komponenten), holst du ihn aus einer benannten View statt ihn inline im Tab zu schreiben:

Wann inline, wann show? Wenn der Tab-Inhalt zwei, drei Zeilen ist – inline. Wenn er ein eigenes Mini-Formular oder eine Liste ist – ausgelagert. Lange Tabs mit inline-Content machen die Tab-Definition unlesbar.
