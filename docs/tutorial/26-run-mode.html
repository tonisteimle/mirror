Run-Mode & Validierung

Interaktives Preview, Lint-Markers, Quick-Fix

Im Standard-Modus kannst du das Preview anschauen, Elemente selektieren und Properties ändern — aber Buttons reagieren nicht auf Klicks, States cyclen nicht. Im Run-Mode schaltet Studio das Preview in einen interaktiven Zustand: Buttons sind klickbar, States cyclen, Form-Inputs editierbar. Daneben hat der Editor Lint-Markers, die Fehler im Code direkt anzeigen — mit Quick-Fix wo möglich.

Run-Mode toggeln — interaktives Preview

In der Toolbar oben (oder mit Cmd+R) toggelst du zwischen Edit-Mode und Run-Mode. Im Run-Mode wechselt der Cursor sich, Selektion-Indikatoren verschwinden, und das Preview verhält sich wie eine echte Anwendung:

  • Buttons reagieren auf Klick — toggle() wechselt den State, show(…) blendet Elemente ein
  • Inputs sind editierbar — Bind-Werte updaten Daten-Variablen in Echtzeit
  • States cyclen wie definiert — Tabs, Toggles, Multi-States funktionieren
  • Navigation und Routing zwischen Screens sind aktiv

Damit testest du das Verhalten ohne separates Build und Deployment. Zurück in den Edit-Mode mit demselben Toggle — State des Run-Modes wird zurückgesetzt.

Validierung im Editor — Lint-Markers und Quick-Fix

Während du tippst, validiert Studio den Code gegen das DSL-Schema. Fehler erscheinen als rote Wellenlinien unter dem Problem; Warnungen als gelbe. Hover über die Markierung zeigt einen Tooltip mit der Erklärung.

Beispiele: bg #2271 — ungültige Hex-Länge, rot. fs bold — bold ist weight, nicht fs; gelbe Warnung mit Quick-Fix-Vorschlag „Property zu weight ändern". Cmd+. öffnet das Quick-Fix- Menu, akzeptiert mit Enter.

Lint-Status der ganzen Datei steht oben rechts: 0 Probleme bei sauberem Code, sonst Anzahl mit Klick- Drilldown auf die Zeilen.

Das Prinzip: Edit-Mode für das Bauen, Run-Mode für das Testen — beide Modi nutzen denselben Code. Validierung läuft live mit, du musst nichts manuell triggern; was rot ist, baut nicht; was gelb ist, baut, ist aber suboptimal.
